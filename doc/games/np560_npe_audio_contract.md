## 2026-10-01：区分原程序 DAC 停启与网页播放队列耗尽

## 2026-09-30：离线解码已得到候选 PCM，客机 ROM 交接仍待验证

[来源记录](../audio/np560_audio_codec_provenance.md) 已新增官方 CYBIT MobiVoice DLL 候选：
十档帧长度/码率与原 PRG format 9..18 完全对应，mode 5 对 format 13 的
21-byte/20-ms/160-sample 推导，原 NPE section 16 可连续解出 1332 帧。
压缩输入按 16-bit 字交换字节后，异常削顶率由 7.56% 降至 0.12%。
这是比参数表更强的码流兼容证据，但尚无原厂 ROM PCM 对照；实验 WAV
不是模拟器已发声的证据。下一步在客机调用点核实 `00:8800` 流字节和
`B6DE/B816/B7AA` 游标/输出契约，保留原厂增益、重复及 DTU/DAC 路径。

### `B6DE` 首停点的客机流窗口实测

使用只含 `ACD8 → RETS` 的隔离诊断 ROM 重演真实矩阵路线，到达
`25:DFD0 → 01:B6DE` 后，透过 Web 桥的只读 `source=data` 读取
`00:8800`。将 4096-byte 窗口与原始《英雄传奇》section 16 逐字节比较：
**前 1024 bytes 完全相同，随后 3072 bytes 全为零**；原 NPE 对应位置不是零。
section 起始是 `20 0D 05 34 F1 6B CA 68…`，首 512 bytes 的双方 SHA-256
同为 `76bf449f3afa661a049099fb195ebb1324f1aea3a327ff3f9dd03e46e4c5b32c`。
证据与可复跑比对工具：`tmp/np560-npe-audio-byte-20260930-v1/stream-window.json`、
`scripts/probe_np560_npe_stream_window.py`。隔离 QEMU 已退出，未触碰用户试玩进程。

这证明原始 NPE 码流进入了客机 RAM，且 `B6DE` 收到的 `00:8800` 不是随意猜的
固定素材地址；**不能推断整段音轨常驻此处**。1024-byte 窗口与 21-byte 帧不整除，
因此后续 `B7AA` 或其底层读位服务必须能跨窗口续读，不能仅从初始 RAM 快照
顺序读取全部 1332 帧。续读回调、边界时间和游标更新尚未取得原厂 ROM 的动态证据。
静态入口 `2F:66F2` 在两个状态分支都先调用原 PRG `2A:87EA`，随后向缺失
`01:B84E` 传 `00:8800` 与 `[51:2AFC]`；`2A:87EA` 又会调用原 PRG
`2C:0D72/0DCA`。这给续读/重定位提供了明确的原代码调查路径，
但目前不能把这些调用的精确副作用当成已动态验证的 refill ABI。

### 原 PRG 已有的音频字节换序阶段

`25:E154..E234` 的正常装载分支最多请求 `0x400` bytes 到 `00:8800`；
`25:E204..E218` 将返回字节数右移 1 位作为 word 数，调用完整原 PRG
`2C:0E1E..0E5C`，随后 `25:E230` 调缺失的 `01:B84E` 更新流状态。
`2C:0E1E` 对每个读取的 16-bit word 执行 `ROR #8` 再写回原处。
扩展 `scripts/probe_np560_npe_audio_contract.py`，在完整原 PRG 上以两个
人工 word `0x1234,0xABCD` 执行该函数：count 2 后成为 `0x3412,0xCDAB`，
count 0 不改动，前后哨兵不变；普通和 icount=5 共四项均通过。
证据 `tmp/np560-npe-audio-swap-contract-20260930-v3/report.json`，整套 30 项均通过。
这把离线候选解码实验所需的**连续 16-bit 字节交换**与原厂播放路径接上，
但尚未实际运行到 `B84E/B7AA`，不能据此声称它们已实现。

## 1. 头解析器会查看前六字节，但不代表必须跳过六字节

原厂 `2C:0C56..0D70` 接收输入 far pointer，保存/恢复 DS0、DS1 和 R2，
将结果放进 `51:2828..283C`。format 13 分支有三次 word 读取。

以已取得的《英雄传奇》section 16 起始六字节 `20 0D 05 34 F1 6B` 为输入，
在当前 QEMU 执行完整原字节函数，再以 `20 0D 05 34 00 00` 作合成对照：

| 状态 | 原始六字节 | 只将末两字节换零 |
| --- | --- | --- |
| `282A` 格式号 | 13 | 13 |
| `282C` 计数 | 1332 | 1332 |
| `282E` 未命名字段 | 63 | 0 |
| `2836` 未命名字段 | 3 | 0 |
| `2830/283C` | 8000 / 8000 | 8000 / 8000 |
| `283A` 格式表值 | 8400 | 8400 |

因此 `282E/2836` 不是仅由前四字节或格式号决定的固定配置。
它们来自第 5/6 文件字节组成的 little-endian word `w`：
`282E = (w >> 4) & 3F`，`2836 = w >> 13`。
原始文件的 `4 + count*21` 长度关系仍成立，但这个函数只查看数据，没有返回或安装
解码器位游标。真正初始位置由缺失的 `B6DE/B816` 决定；不能因读取了六字节就改为
“六字节头”，也不能据长度关系强制让解码器从第 5 字节开始。

## 2. 原厂格式表不是采样率表

`2C:0C98..0CB2` 从 `32:B7A8` 按格式号索引，取得下列值；index >24 回到 index 0。

| 格式号 | 表值 |
| --- | --- |
| 0 | 0 |
| 1..5 | 800、1200、2000、2400、2800 |
| 6..8 | 0、0、0 |
| 9..18 | 3600、4800、6000、7200、8400、9600、10800、12000、13200、14400 |
| 19..24 | 6500、9100、11800、14500、17200、19800 |

表存在不等于原厂 NPE 播放入口接受全部编号；`25:02D0..0410` 的 >=19 拒绝分支
仍按 [来源边界](../audio/np560_audio_codec_provenance.md) 保留。后续历史官方资料已将 9..18 十档
与 ESAC-4 参数族完整匹配，见该文第 5 节；这是来源强线索，不是已验证码流兼容。

`26:8D2A` 先调用 `B816` 取得指针与余位，然后进行三次 `B7AA` 试解码。
每次用处理前后的 `(far_pointer 差)*8 + 余位差` 求消耗位数，更新 `51:29D0/29D2`。
它是在测量解码器的实际位步长，**不是在原厂 PRG 中直接写死 21 bytes 或 168 bits**。

`26:8E68..8EE0` 使用该步长 D 和 `283A` 表值 B 做下列整数计算：

```text
Tq12 = floor((D * 40960) / floor(B / 100))
total = floor((floor(Tq12 / 16) * count) / 256)
```

这里 `33:07B0` 是 32-bit 乘法（保留低 32 位），`33:24EA → 31:6A14` 是
32-bit 无符号商；公式限于正常范围、非零除数，不能忽略一般情况下的整数溢出。
该分支为此类格式构造毫秒时间与 Q12 换算量；`283E/2840` 存总时间，
`2842/2844` 后续也被 `2F:66F2` 从播放时钟 `4A52/4A54` 更新。
因此表 B 在原厂时间换算中充当压缩 bit/s，不是 PCM Hz。
本段来自完整指令的静态分析，**没有用成功桩执行三次缺失解码服务**。

## 4. 对实际声音恢复的约束与剩余未知

`2E:7FE4` 接收 `B7AA` 返回量 N 后令 `2AFA = N >> 1`，分两期处理输出。
每期对 `2984 + phase * (N >> 1) * 2` 的样本做原厂增益、4 倍 word 重复，再调用
`AD92`，设置 DTU 每期数量 `4 * (N >> 1)`。`25:DF62` 使用输出选择码 3，
按已核对的配置表是 32000 Hz。返回量因此作为解码样本数使用，不是压缩字节数。
对于偶数 N，两期共输出 4N 个样本，时长为 N/8000 秒；奇数、特殊状态和错误返回
尚无缺失服务的约束，不能自行补齐。

**条件推导：** 如果一次真实 `B7AA` 消耗 168 bits，B=8400 时对应 20 ms；
与上述输出节奏一致的 N 将是 160。文件 `4 + 1332*21` 也与此一致。
但现在还没有真实 B7AA 的 D、N 或 PCM 输出，不能将此一致性升级为“帧格式已证实”。
